## Consumer contracts and failure boundaries

Schemas and exported response types in `packages/contracts/src` plus each owning `*.routes.ts`/`*.controller.ts` are the executable transport reference. Existing API guides above and #20–#23 implementation contract tables describe request/response/denial/retry/output semantics. This gate introduces no alternate protocol. The attachment quota test seeds retained metadata near 2 GB and exercises real valid 20 MB/file I/O plus API reservation races; it does not write 2 GB of physical files or establish storage/load capacity. Cookie authentication, session-derived clinic, ready-account checks, Origin/CSRF writes, no-store and current authorization remain server-side. Consequential operations use existing transaction/idempotency seams; retries must retain the same command/payload and reauthorize. Stale revision or changed-payload reuse requires reconciliation, never silent overwrite.

Permission tests include doctor, doctor-manager, non-doctor manager, permitted/restricted staff, historical-only and disabled accounts; clinic/patient identifiers are not authority. RLS is separately probed through the restricted runtime pool; administrative fixtures and test-only failure triggers are not the runtime authorization connection. Time/mail/private storage failure boundaries may be injected; no live email, external provider, real patient or production database is used.

Collections are **not** universally paginated: inventory/history projections return full authorized collections, autocomplete/search endpoints have their own bounded query contracts, and exports explicitly reject sources over documented limits. No unbounded-volume/load/performance acceptance or generic cursor protocol is inferred. Frontend consumers must follow each actual contract rather than invent pagination, document rendering or guaranteed replay after expired export deletion.
