## Proposed deployment adaptation

Keep the approved Compose stack: Nginx serves the SPA and proxies `/api/v1` to one Express process; PostgreSQL and private attachment volumes remain internal. On this host, use Dokploy's existing Traefik entry point for public HTTPS and forward to the internal Nginx service. Do not bind another Nginx to host ports 80/443. Attach only the Nginx entry service to the ingress network; API/database use a private application network, with no public database/API ports. Validate the effective networks generated by the installed Dokploy version.

The owner approved this layout on 2026-10-10. This changes the TLS termination location from the generic architecture diagram while preserving Nginx and same-origin API behavior. Configure trusted proxy hops explicitly across Traefik/Nginx, overwrite forwarded headers at trusted boundaries, and verify secure session cookies, client-IP rate limits and redirects through both proxies. Verify SSE flushing, heartbeat, disconnect/reconnect and timeout behavior through the entire route. Never globally trust arbitrary forwarded headers.

Dokploy documents Traefik routing labels for Compose domains and reserves ports 80/443 for its ingress. Domain ownership, HTTPS provisioning and the installed version's configuration remain deployment gates. ## Proposed measurable performance acceptance

The owner accepted this performance baseline through the decision popup on 2026-10-10. These are acceptance targets, not observed results or purchased service guarantees; backup implementation verification and recovery feasibility remain outstanding. Use an isolated Linux environment matching deployment and fictional data: 10,000 patients, 50,000 appointments, 100,000 procedure/financial records and up to 1 GB attachments. Run five active browser users and ten concurrent authenticated sessions/SSE streams for 30 minutes after warm-up; overlap a backup once. Record hardware, data generation, network, raw timings and query plans.

| Measure | Proposed pass threshold |
| --- | --- |
| Routine patient search, schedule and patient-summary API reads | p95 <= 500 ms at API boundary, paginated results |
| Ordinary database writes | p95 <= 750 ms, excluding upload/export and deliberate rate limiting |
| Authorized SSE invalidation after commit | p95 <= 2 seconds at receiving browser on a stable connection |
| Browser patient/schedule navigation | p95 <= 2 seconds after initial load on pilot PCs/network |
| Server failures | Unexpected HTTP 5xx < 1% of valid requests; zero lost committed records, duplicate consequential writes or isolation violations |
| Capacity headroom | No OOM/restarts; >= 20% free disk; record CPU, RAM and backup interference, then set service limits from measurements |
| Recovery | Joint recoverable data point <= 60 minutes old and full replacement-host rehearsal <= 60 minutes |

Measure initial browser load separately on the actual clinic connection; its bandwidth/latency is unknown. Correctness and clinic isolation remain mandatory independently of percentile thresholds. Authentication hashing, exports and attachment limits require their own workload checks when those tickets define the contracts. Do not use arbitrary delays or skipped checks to make the targets pass.
