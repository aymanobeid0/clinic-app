### Approved consultation journey — standalone integration gap

- **Independent of a treatment plan**: no dummy plan/procedure prerequisite. Existing/returning patient or inline registration if absent; do not duplicate a returning patient's identity.
- Can be booked now or later under scheduling rules. Appointment linkage is optional. Linked consultation appears in its appointment day's calendar cell, not the payment day. Doctor-agreed emergency/walk-in consultation needs no booked appointment; appears in **doctor's today's consultations**, marked **without appointment**, opening details/patient record.
- One system default price, editable by authorized reception/doctor for that consultation at booking; individual edit does not change other bookings/default. Existing exact-currency/capability boundaries remain.
- Payment optional at booking or later, **full-only**, not partial. A booking can be confirmed unpaid. Record payment **when actually paid**, using normal payment/receipt behavior; paid status is backed by records, never an invented payment flag.
- Latest correction: unpaid consultation becomes debt only when the patient **enters the doctor's room**, recorded explicitly in the app, not on booking/opening details. Actual consultation payment enters the doctor's share immediately, including before room entry. Dedicated prepaid funds cover the charge on entry with no second payment/receipt/share.
- Examination note belongs in the patient record; consultation may end with the note unfinished and accessible in pending notes.
- Latest owner direction: **keep it simple**. Refund uses the system's normal workflow and authorized approval. No consultation-specific cancellation-policy interview or exception process. Preserve other treatments' installment support.

### Shared screen states and recovery

| State | Required behavior across the relevant screens |
| --- | --- |
| Loading / refresh / empty | Show pending; empty only after successful empty response. Failed refresh is not a new zero balance/empty day. Preserve distinctions between drafts/final/correction, planned/started/completed, due/credit and current/historical versions. |
| Validation / business failure | French safe field/cause guidance; retain valid non-secret current-tab input. Login keeps identifiers and clears password. Stock/financial prerequisite failure is not automatically stale revision. |
| Denial / scope change | Real account/patient/content authorization on server, including direct navigation. Retire confidential snapshots, feedback, commands and downloads as scope changes. Do not expose concealed records or bypass genuine denial. |
| Conflicting edit | Refetch current revision/history; explicitly reconcile recoverable input and reconfirm. No silent overwrite, automatic rebase or copied revision-only retry. |
| Network / uncertain result | Say outcome is unconfirmed; preserve exact consequential command ID/path/payload for retry even if visible inputs changed. Check server state; never use a fresh command to escape uncertainty. No offline/persistent sensitive drafts. |
| Cancel / leave / reload | Cancel unsubmitted input without a write. Closing/aborting response cannot cancel an already submitted server write. Account/patient change retires workflow and late results. Navigation must account for unsaved/uncertain input; tab-memory drafts may be lost on reload. Domain cancellation is separate from closing a form. |
| Session / CSRF / throttling | Follow actual cause: reconnect, refresh security context before explicit write retry, or wait. Status alone does not prove cause. |
| Files / print / export | Current authority before bytes/output; generated is not delivered/printed. Expiry/cleanup permits regeneration. `export_scope_changed` retires old receipt and permits new server-authorized generation; real denial stays locked. No historical application output. |
