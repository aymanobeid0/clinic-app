# Operational reports and follow-up API (#26)

Backend acceptance only. Frontend logic belongs to #59; designed shell and report/follow-up pages to #60/#73; connected coverage and scaffold retirement to #76. These requirements remain outstanding. No product UI, automated messaging or advanced BI is included.

All routes use the existing authenticated session, clinic derived from membership and `Cache-Control: no-store`. Writes require same-origin and the session CSRF token. Disabled, onboarding and historical-only accounts cannot use these operations. Every request, including retry, history and share preparation, checks current access. Never accept a client clinic ID. Shared schemas/types live in `packages/contracts/src/reporting.ts`.

| Method/path (under `/api`) | Contract |
| --- | --- |
| GET `/reports/appointments?date=YYYY-MM-DD` | `{date, appointments: Appointment[]}` using the existing scheduling contract. UTC day, includes appointments overlapping midnight, all statuses retained. Requires `reports.operational`; ordinary doctors see only active assigned/shared patients. |
| GET `/reports/financial?date=YYYY-MM-DD` | `FinancialReport`: selected UTC day's activity and **current** balances at `balanceAsOf`, not a historical balance snapshot. Managers have financial report authority; others require both `reports.financial` and `billing.read`. |
| GET `/reports/stock` | `{asOfDate, settings, lowStock, expiring, expired}` using inventory item/batch contracts. Requires `reports.operational` and `inventory.read`. Same current UTC date, expiry warning settings and movement-adjusted availability as `/inventory`. Only active low-stock items and positive remaining expiring/expired batches. |
| GET `/follow-ups` | `FollowUpList`: persisted contact `tasks` (open and completed) plus derived `pendingNotes`. Requires `reports.operational`. Contact tasks follow operational patient scope; pending-note metadata additionally requires current `clinical.read` and active clinical patient scope. |
| POST `/follow-ups` | `createFollowUpSchema`: `{commandId, patientId, dueOn}`; creates one `contact_patient` task at revision 1, status `open`. Returns `FollowUp`. |
| POST `/follow-ups/:id` | `updateFollowUpSchema`: `{commandId, revision, status, dueOn?}`; status `open` or `completed`; optional date reschedules. Returns next `FollowUp` revision. |
| GET `/follow-ups/:id/history` | `{events: FollowUp[]}` with retained revisions, actor and date. Same patient authorization as task list. |
| GET `/follow-ups/:id/share` | `ManualFollowUpShare`: `{delivery:"manual", text}`. French contact-only message from current authorized patient/clinic identity. Safe to retry: sends nothing, stores no delivery status and calls no messaging provider. The person chooses whether/how to share. |

Appointment/financial date queries are strict and reject invalid dates or extra fields. IDs are UUIDs, dates are ISO calendar dates. Task payloads are strict; patient/clinic identity, actor and revisions cannot be overridden. No clinical free text is accepted in contact tasks or included in share content. Pending-note IDs are `note:<visit UUID>`, read-only: finalize/correct via the existing note API, not contact-task commands. Ended visits with no finalized note or a correction draft remain pending; finalization resolves them. Note text/history never appears in task metadata. No new permission grants, automatic task scheduling, delivery worker or notification subscription is introduced; consumers refetch after relevant existing SSE invalidations and reconnect.

Financial results group exact integer minor-unit strings by currency, with no conversion. Each patient row includes scoped totals, invoice summaries and payment activity. Nonclinical staff receive neutral identity/references/amounts, never procedure descriptions or notes. Ordinary doctors require active patient scope and see only their own performed work. Mixed receipts contribute only allocations to their charges, excluding deposits and other doctors' allocations; receipt numbers do not authorize retrieval of the original document. Inseparable mixed-doctor invoices are omitted, consistent with the invoice API.

`newMoneyMinor` is gross new receipts on the selected day, including explicit deposits; `appliedCreditMinor` is credit allocated that day, never another receipt. `openingMinor` records opening debt entered that day (not its legacy `asOf` date); `adjustmentMinor` is signed charge adjustment activity. `refundMinor` is executed refunds, `reversedMoneyMinor` erroneous new receipts reversed that day; neither is counted as an additional payment. `invoiceMinor` is issued invoice activity, never new debt or cash. Activity remains immutable: original receipts and their later reversals appear on their respective days. `dueMinor`, `creditMinor` and `plannedMinor` are current authoritative billing balances; planned unstarted treatment is separate from debt, credit separate from debt, and adjustments/releases/reversals affect current balances through billing reconciliation. Archived patients remain included where authorized.

Task events append atomically under the existing clinic transaction lock with restricted runtime RLS, composite patient/actor clinic references and no UPDATE/DELETE grant. Command IDs are clinic-unique and bound to actor plus parsed payload/path. Identical retries return the original event after current authorization; reuse with different payload/actor is 409. Stale task revision is 409: fetch current state/history, review, then submit a new command. Concurrent competing edits cannot silently overwrite. A failed transaction leaves no task/event; retry the same command after recovery. Create task ID equals its creation command ID. Essential history is free.

Errors follow existing JSON middleware: 400 invalid transport, 401 absent/expired/revoked session, 403 missing capability, 404 inaccessible/missing task or patient, 409 command/revision conflict, sanitized 500 for storage failures. Report failures return errors, never fabricated zero totals. Retrying a GET has no delivery effect. No production migration, deployment, real-data use, load benchmark or final browser acceptance is established by local tests.
